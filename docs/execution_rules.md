# InsightOps 执行规则与可复用优化原则

> 生效日期：2026-08-22。本文记录用户明确提出的长期规则，以及在项目执行中验证有效的流程优化。后续如有新规则、例外或改进，必须追加并注明来源与生效范围。

## 1. 步骤化交付与明确确认

1. 每次开始一个项目阶段时，明确说明“这是哪一步、目标是什么、需要哪些输入或依赖”。
2. 每次完成一个项目阶段时，明确向用户说明：`步骤 N：名称，已完成；总结已写入 docs/project_progress.md。`
3. 每个步骤的总结必须包含：原定目标、实际完成、问题、解决方式、证据文件/批次/运行 ID、未解决边界和下一步。
4. `docs/project_state.md` 是当前状态检查点；`docs/project_progress.md` 是不可省略的历史总结。

## 2. 最高优先级执行与降级规则

1. 默认采用原定方案中质量、可追溯性和可复跑性最高的可行实现，不因方便而静默降级。
2. 若最高优先级方案需要下载、安装、登录、权限、付费授权或用户提供文件，必须在执行该步骤时立即指出具体缺项和用途，等待补齐后继续。
3. 只有最高优先级方案无法取得、用户拒绝、成本/权限不适合或技术上不可行时，才提出较低优先级方案；必须记录原因、功能损失和未来回补条件。
4. 不得把公开样例、轻量样本或合成数据描述为真实生产数据；任何字段/时间/粒度边界必须进入数据访问或质量文档。

## 3. 数据工程与验证标准

1. 每份外部输入数据必须记录来源、提取方式、日期范围、文件名、SHA-256、行数与字段契约。
2. Raw 层只追加，使用 `batch_id`、来源哈希和源文件行号追溯；禁止覆盖已有批次。
3. 下游 Staging 只接收通过对应质量运行的记录；BLOCKER 失败必须阻断并保留拒绝记录。
4. 每次导入或转换后至少核对行数、日期范围、关键业务事件/指标与来源是否一致。
5. 对会影响订单、收入或客户价值的警告，必须在对应事实表中实施显式去重或排除规则，不能仅在报告中说明。

## 4. 执行优化与上下文连续性

1. 每个重要里程碑完成后更新 `docs/project_state.md`，确保长对话摘要后仍能快速恢复项目状态。
2. 进行长耗时或有外部依赖的操作前，先说明当前动作和预期验证；操作完成后报告实际结果。
3. 优先创建可重复执行的脚本、SQL 与 notebook；一次性手工操作必须留下等价的可复跑说明。
4. 发现规则设计、字段语义或数据边界与实际数据不符时，先基于审计结果修正规则，再重跑；保留历史运行作为决策证据。
5. 当前 Codex 桌面任务不提供可由代理读取的实时上下文占比；使用项目状态检查点配合系统自动摘要，不将“自动摘要”误称为手动可控功能。

## 5. 每步自检与测试

1. 从步骤 9 起，每个步骤完成前必须执行与该步骤相匹配的自检：至少包括代码静态检查、实际运行或查询核验，以及关键结果的来源/口径对账；不以“文件已创建”代替验证。
2. 自检优先覆盖本步骤新增或修改的 SQL、脚本、数据表、Notebook 和指标定义；只在发现跨步骤影响时扩大检查范围，避免无差别重查整个项目。
3. 步骤总结必须增加“自检与测试”小节，记录执行的检查、通过结果、未覆盖边界及其后续补测计划。
4. 若自检失败，先修复并重跑本步骤检查；如需改变既有口径或影响已完成事实，必须记录变更、影响范围和新的运行证据。
